# Прикладные сценарии QSL 0.4.0

Проверяемая схема имитирует API телеметрии. В ней один из трёх payload API (Reading, Update, Notice), а для сокетов предусмотрены Heartbeat и Event. Вложенные Context, Geo, Auth, Patch, Limits и Retry имеют независимое присутствие. Набор из 256 записей на сценарий включает пустые строки, нули, false, пустые списки и отсутствие необязательных полей. Все варианты сверены по полной структуре. [Описание модели](realistic/src/model.rs) · [HTML с фильтрами и расчётом](dashboard.html)

QSL кодирует тип payload явным дискриминантом. Вложенные переменные записи кодируются сгенерированными проверяемыми QSL-кодеками и вкладываются как массивы байтов с длиной. Время и аллокации этой сборки учтены. Proto3 использует oneof и explicit presence. Cap’n Proto использует union, признаки присутствия для скаляров и указатели для вложенных записей. Bincode использует Rust enum и Option, конфигурация standard / varint. Cap’n Proto измерен в обычном и packed режиме.

## HTTP API

POST /v1/normalize принимает бинарный запрос, создаёт модель, проверяет ветку, увеличивает revision и возвращает новый бинарный кадр. k6 предварительно загружает те же 256 запросов, затем проверяет каждый байт ответа. HTTP/1.1 с keep-alive на localhost, 8 VU, 2 с прогрева и по 8 с измерения, два противоположных порядка. Числа включают HTTP-путь и работу клиента. Модель без TLS и базы данных. ## TCP Heartbeat / Events

Один постоянный TCP-сокет на испытание. Клиент отправляет Heartbeat и проверяет ответ с новой ревизией, затем одним вызовом записи отправляет пакет из 32 Events и ждёт ACK. Сервер декодирует все события и проверяет ветку, возвращая число и контрольную сумму идентификаторов и списка affected. Форматы делят одинаковую длину-префикс 4 B. ACK занимает 12 B + 4 B префикса и учитывается в среднем объёме на событие. RTT исключает подготовку отправляемых кадров и клиентскую сверку. Events/с вычислены по активному времени пакетов с ACK. 128 прогревочных и 2048 измеренных циклов в двух порядках.
