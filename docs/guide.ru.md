# QSL. Полное руководство по проекту

## Безопасный вход и идентичность

Checked API генерируется для каждой схемы. `!config MAX_DATA_SIZE = 65535;` ограничивает кадр, восстановление QPS и общий объём значений. Строгий и лёгкий хэши вычисляются при анализе; `!config USE_HASH = xxHash;` выбирает XXH3-64, xxHash128 — 128 бит. Оба атрибутных макроса подключаются из qsl; реализация находится в qsl/macros. [Полный контракт безопасности](safety.ru.md) · [Идентичность схем](schema-hashes.ru.md).

## Назначение и границы

Исходная задача QSL — обмен заранее описанными данными. Типы, диапазоны, порядок полей и правила владения известны до запуска программы. Генератор превращает эти условия в специализированный Rust-код. Динамический разбор схемы не входит в каждую операцию чтения и записи.

QSL — конструктор кодека, зависящий от условий проекта. Разработчик задаёт инварианты, выбирает формат и готовит память. Цена этого подхода — явные решения о совместимости, размерах, времени жизни и проверках. Выигрыш возникает там, где заранее известные условия позволяют убрать повторную работу.

Все дополнительные механики и атрибуты опциональны. Порядок полей обязателен всегда: сначала обязательные, затем опциональные. Изменение порядка, диапазона, кодека, кванта или конфигурации может изменить wire-format. Обе стороны должны использовать согласованный формат.

Общее квантование QPS восстанавливает весь переданный payload. Числовая специализация QPS упаковывает статически известные диапазоны. Предиктование по длине выполняют opt_table и predict_seq. Квантование само по себе не определяет наличие полей.

## Минимальное подключение

В зависимостях приложения и build-зависимостях используется одна версия QSL. В build.rs явно перечисляются QSL-, DEQ- и Rust-файлы шаблонов. Функции build_qsl_files / build_qsl_files_with_rust записывают qsl_gen.rs в OUT_DIR. Приложение подключает этот файл через include!.

```rust
let out = std::path::PathBuf::from(std::env::var_os("OUT_DIR").unwrap());
qsl::build_qsl_files(&["schema.qsl"], &["schema.deq"], &out)?;
// В модуле приложения:
include!(concat!(env!("OUT_DIR"), "/qsl_gen.rs"));
```

```qsl
&Message[opt_table] {
    u32 id;
    str(0..4096) text|binary_opt=guard|;
    u16? code;
}
```

Проверяемый вход доступен каждой схеме; safety сохранён как совместимый атрибут. opt_table выбирает статический граф optional-хвоста. Ни один из этих атрибутов не делает произвольный указатель безопасным и не отменяет ограничения custom-кодека.

## Цепочка сборки

1. DEQ разбирает типизированные константы и опциональную конфигурацию генерации.
2. Парсер QSL вычисляет выражения, проверяет объявления и строит схему.
3. Rust-шаблоны раскрываются в поля; проверяются циклы, имена и окончательный порядок.
4. Анализатор вычисляет диапазоны, битовые ширины, границы событий и допустимые регистры.
5. Интерпретатор генерирует структуры, константы, методы и статические таблицы.
6. rustc/LLVM выбирает инструкции и окончательную раскладку нативных объектов.

Анализ Zed использует тот же native-парсер, если найден совместимый qsl-analyze. Предварительная JS-оценка помечается. Список файлов редактора служит подсказке; список build.rs определяет фактическую сборку.

## Язык схем

Объявление имеет вид &Name[атрибуты] { тип имя|модификаторы|; }. Знак ? делает поле опциональным. Теги назначаются по порядку компилятором; пользователь не переопределяет их. Повторные имена, неверные диапазоны и обязательное поле после optional-поля отклоняются.

Границы A..B включительны. Выражения констант поддерживают +, -, *, /, %, скобки, именованные значения и sizeof для поддержанных целых типов. Переполнение и деление на ноль являются ошибкой сборки. sizeof в DEQ относится к указанному целому примитиву, а не к произвольной будущей структуре Rust.

Прямой текстовый парсер поддерживает u8/u16/u32/u64 и i16/i32/i64. Внутренняя модель умеет описывать i8, однако прямой i8 не входит в список примитивов этого парсера. Неизвестное имя может означать custom-тип и потребовать QslCustom; оно не становится автоматически встроенным числом.

## Обычный формат

Обычные целые записываются little-endian в нативной ширине. str имеет длину u32 и UTF-8-байты; фиксированная строка не хранит длину. Динамический массив хранит количество и элементы, фиксированный — известное схеме количество. Физические поля идут в порядке схемы, независимо от расположения объекта Rust.

Для одного optional-поля обычный формат использует присутствие. Для нескольких обычный режим хранит число присутствующих полей и их теги. tag_bits=ceil(log2(max_tag)), count_bits=ceil(log2(optional_count+1)); в обычном байтовом режиме метаданные выравниваются до целого байта. Фактический заголовок может зависеть от числа присутствующих полей.

Указательный decoder обычного формата предполагает правильные теги и достаточный вход. Checked API отдельно проверяет кадр. Формат не содержит универсального описания типов на каждый запрос.

## compact и alignment

compact кодирует ранг x-min. Требуемая ширина B=bit_length(max-min). Для единственного допустимого значения B=0. Поля могут пересекать границы байтов и машинных слов; анализатор выбирает регистры и разворачивает операции.

Пример: диапазоны 0..7, 0..31 и 0..1023 занимают 3+5+10=18 бит, то есть 3 wire-байта. Нативные типы и их Rust-размеры остаются прежними.

alignment при compact завершает каждое поле на байтовой границе. Это wire-выравнивание, а не выравнивание буфера на кеш-линию. Дополнительные биты могут упростить доступ, но увеличивают кадр; эффект проверяется парным замером.

compact несовместим с предиктивными последовательными режимами. Для активной числовой специализации QPS compact, alignment, bitmap и legacy-каталог не складываются произвольно: недопустимые сочетания отклоняются анализатором.

## Optional-поля и default

Окончательный порядок после раскрытия Rust-макросов также обязан быть [required][optional]. Теги инкрементальны. Перенос полей меняет формат и выполняется только явно.

Модификатор default задаёт числовую инициализацию Rust Default, но не превращает отсутствующее поле в присутствующее. Декодирование отсутствующего поля возвращает None. Some(константа) сохраняет отдельный факт присутствия, даже когда значение не требует payload-битов.

optionals=bitmap выделяет бит для каждого объявленного поля, включая обязательные, и хранит полные little-endian слова u32. Биты обязательных полей должны быть установлены. Для маленькой схемы четыре байта метаданных могут оказаться дороже обычного заголовка. Порядок полей определяет позиции битов.

## predict_seq

Самостоятельный predict_seq использует длину кадра для последовательного optional-хвоста. Для единственного поля конец обязательной части отличает отсутствие от присутствия. Для нескольких фиксированных размеров анализ требует однозначных сумм в пределах бюджета. Неоднозначный набор не угадывается.

Present-поле нулевой wire-длины нельзя отличить от отсутствующего только по EOF. Нужен length-aware decoder. Вызов deserialize_unsafe(ptr) без длины для такого режима не поддерживается; это ограничение API, а не обещание безопасной обработки произвольных байтов.

В сочетании opt_table,predict_seq атрибут выбирает прямые числовые выражения вместо косвенного вызова функции события. Формат остаётся форматом opt_table. Политика inline задаётся независимо.

## opt_table: предиктование по длине

opt_table хранит критические границы и функции рядом со сгенерированным типом. Таблица не выделяется на каждое сообщение. После обязательной части и известной метаобласти вычисляется длина optional-payload L.

Индекс события имеет вид I(L)=sum((L>c_j) as usize). Внутри события известны гарантированные и возможные поля. В однозначном состоянии теги не читаются. При неоднозначности читаются только необходимые метаданные; зарезервированный wire-байт от этого не исчезает.

Для двух optional-u8: I=(L>0)+(L>1). L=0 означает отсутствие обоих, L=2 — наличие обоих, L=1 требует различить a и b. Для строк 3..33 и 1..255 одни интервалы определяют наличие description, а другие остаются неоднозначными. Длины и правила их учёта строятся по схеме, а не задаются числом 34 вручную.

CRITICAL_POINTS задают границы, EVENT_TABLE — обработчики, OFFSET_TABLE — функции смещений. Соседние эквивалентные интервалы объединяются. Границы не требуют массива на каждый возможный байт длины. Общий анализ ограничен 12 полями и 65535 payload-байтами; равные фиксированные ширины поддерживаются до 64 полей. Вне возможностей анализа выбирается явный fallback.

opt_table=legacy сохраняет прежний каталог смещений внутри сообщения. Это отдельный формат. Квантованный внешний payload сначала восстанавливается; смещения обычного кадра нельзя применять к его сжатым байтам.

Контроль предыдущего снимка уже показал замедление чтения opt_table при некоторых N. Атрибут не считается ускорением по одному наличию таблицы. В свежем обзоре отдельно измеряется схема с уникальными суммами размеров.

## Строки, UTF-8 и владение

| Выбор | Rust | Что происходит при чтении |
|---|---|---|
| Обычная строка | String | Создание и заполнение собственного хранилища |
| lifetime | &'a str | Заимствование входных байтов |
| binary_opt=true | &'a [u8] | Заимствование UTF-8-байтов |
| binary_opt=view | Utf8Guard<'a> | Строкоподобный заимствованный вид |
| binary_opt=guard | Utf8CopyGuard | Копирование в собственный SerOut |
| binary_opt=inline | InlineString<MAX> | Копирование во встроенную ёмкость |
| decompress=true | InlineString<MAX>, либо [u8; N] для фиксированной | Восстановление raw/LZ в конечную область |

Один символ Unicode может занимать несколько UTF-8-байтов. Поэтому в замерах отдельно подписаны 1024 символа и их фактический байтовый объём. Границы схемы и P относятся к байтам.

CopyGuard не заимствует исходный кадр. Первый буфер может потребовать аллокацию; подготовленная достаточная ёмкость используется повторно. InlineString не выделяет отдельную строку, но большой MAX увеличивает размер нативного объекта и рабочий набор, даже если текущее значение короткое.

Заимствованные режимы требуют подходящего lifetime и живого неизменяемого источника. Фиксированные строки остаются [u8; N] при любом binary_opt. Декомпрессированные байты нельзя заимствовать из исходного сжатого представления; нужен регион восстановления.

## Строковое LZ

decompress=true включает специализированный ограниченный строковый кодек. Выбор raw/packed и ширины заголовков определяется схемой и данными. Сжатое представление используется при выигрыше с учётом framing; невыгодный результат заменяется raw-вариантом.

MAX ограничен 65535 восстановленными байтами. Для динамических строк используются ограниченный заголовок и смещения соответствующей ширины; фиксированная строка имеет свой framing. Это отдельный механизм от числовой специализации и общего байтового QPS.

Время зависит от длины, повторов и энтропии. Один удачный повторяющийся текст не характеризует случайный UTF-8. Свежий обзор включает шум и повторяющиеся данные. Порог 25 нс — цель проекта для указанной строки, а не доказанная универсальная гарантия.

## QPS: два точных operand-пути

QPS не предиктует поля. Он преобразует значения в обратимые числовые операнды. Кодек не может уменьшать все возможные входы без потерь; группировка расширяет доступный контекст, но не уменьшает мощность полного пространства значений.

Четыре произвольных u8 задают 32 бита. Если все комбинации допустимы, единственного обратимого представления короче 32 бит для каждой комбинации нет. Выигрыш появляется из заданного диапазона или фактической избыточности. Расширение предупреждает об одиночном u8 без выигрыша.

Числовая специализация [qps] / qps=Q2/Q4/Q8/Q16 вычисляет ранги статически ограниченных чисел. Для r=x-min сохраняются частное и остаток; статические маски и сдвиги восстанавливают исходное число. По умолчанию Q16. quant=Qn — совместимое написание, но оба атрибута вместе запрещены. Константы могут не занимать value-битов; присутствие optional остаётся отдельным.

Общий ByteQps<Q> принимает любые сериализованные байты: числа, UTF-8, массивы и custom-представления. Поддержаны Q=2/4/8/16 байтов в группе. Он не анализирует смысл полей и не заменяет валидацию схемы.

## Общий QPS: формат и математика

Явный заголовок QPB3 занимает 16 B: magic 4 B, квант 1 B, режим 1 B, общая минимальная база 1 B, резерв 1 B, исходная длина u64 little-endian 8 B. Длина не квантуется. Raw-режим хранит заголовок и исходные байты, поэтому его framing-цена видима: 16 B.

Для байтов x_i выбирается база a=min(x_i), ранг r_i=x_i-a. Для каждой группы выбирается B=bit_length(OR r_i), d=2^B и операнд W=sum(r_i*d^i). Группа хранит один байт B и ceil(n*B/8) байтов W. Обратное преобразование: r_i=(W>>(i*B))&(d-1), x_i=a+r_i. Для B=0 вся группа восстанавливается из базы.

Полный packed-кадр выбирается только если 16+sum(1+ceil(n*B/8)) меньше исходной длины. Проверка включает весь заголовок. Для маленького или несжимаемого payload получается raw-кадр; его общий размер может быть больше исходного на framing. Это не скрывается в показателях.

Сложность O(n), вспомогательная память O(1) при переданных буферах. Анализ базы и ширин требует проходов по входу. Q фиксируется параметром типа; ширина выбирает специализированное арифметическое ядро из таблицы. В ядре нет per-byte if. Проверки границ и формата находятся в безопасной оболочке; цикл групп и выбор raw/packed остаются. Отсутствие ветвлений во всём кодеке не заявляется.

Внешний ByteQps восстанавливает точный внутренний кадр, включая его длины строк и массивов. Чтение внутренних полей выполняется после восстановления. Схемный числовой путь и внешний byte-envelope — разные форматы, их нельзя неявно подменять.

Полные группы обрабатываются машинными словами, а не серией мелких memcpy. На x86-64 с BMI2 один выбор реализации вне группового ядра подключает pext/pdep; на остальных машинах сохраняется переносимый путь. u128 здесь — тип операнда Rust, а не обещание одного 128-битного целочисленного регистра. Для неполной группы используется локальный хвост; скрытое дополнение входного среза не требуется. Формат QPB3 после оптимизации не изменился.

После оптимизации Q16 для набора 1024 B со значениями 0..15 даёт 592 B, запись 440.05 ns и чтение 258.01 ns. Бюджет накладных расходов 20–30% и ориентир 25 ns этим общим кодеком не достигнуты. Он остаётся явно выбираемым путём сжатия; числовая специализация и обычное чтение оцениваются отдельно.

## Общий QPS: API регионов

```rust
use qsl::qps::ByteQps;
let frame = ByteQps::<16>::encode_to(input_bytes, encoded_region)?;
let restored = frame.decode_to(restoration_region)?;
assert_eq!(restored, input_bytes);
```

Safe-схемы реализуют CheckedRecord или CheckedBorrowedRecord. Эти unsafe-trait связывают валидатор с точным доверенным decoder. encode_record_to проверяет значения, пишет внутренний кадр в scratch и кодирует его в отдельный output. decode_record_into восстанавливает внутренний кадр, валидирует его и записывает объект в MaybeUninit.

Для [qps] генерируются serialize_qps_to(scratch,out) и deserialize_qps_into(input,restoration,out). Для заимствованной схемы deserialize_qps возвращает объект с lifetime региона восстановления. Раннее освобождение этого региона запрещается системой типов.

Общий путь явно вызывается через эти методы или ByteQps; существующий Serializable-формат не переопределяется автоматически. Числовой QUANT_ACTIVE обозначает специализацию, а не наличие всех QPS API. Удобный serialize() активной числовой схемы и внешний serialize_qps_to имеют разные типы результата и разные правила framing.

Три логические области — исходный нативный объект, encoded-кадр и scratch/restoration. В разные фазы scratch и restoration могут занимать переиспользуемый регион. Кодек не аллоцирует их внутри encode_to/decode_to. ByteFrame заимствует output. Маленькая схема может не окупить 16 B; слепого уменьшения буфера не происходит.

## Специализированные prepared-методы

Числовой QuantizedFrame отличается от общего ByteFrame. Его prepared-путь использует QUANT_PADDING_BYTES — явно инициализированный приватный хвост, который не передаётся по сети. Exact-slice checked API скрытого хвоста не требует.

serialize_quantized_to проверяет значения и ёмкость перед быстрым ядром. quant_write_prepared и quant_read_padded являются unsafe: диапазоны, padding, невзаимопересечение и выравнивание назначения обеспечивает вызывающий код. QuantizedFrame::decode_into восстанавливает объект в отдельную большую область.

Не следует переносить границы обычного сообщения в упакованные смещения. Для активного числового QPS opt_table может дать функции битовых префиксов присутствия. Эти функции используют метаданные, а не предиктуют содержимое сжатого буфера по его байтовой длине.

## Безопасность и методы чтения

| Метод | Что входит | Предусловия |
|---|---|---|
| validate | Проверка целого кадра | Safe-вход; custom обязан дать валидатор |
| deserialize_checked | Проверка и создание результата | Тот же формат и схема |
| deserialize_checked_into | Проверка и запись в MaybeUninit | Для владеющих и заимствованных поддержанных схем |
| deserialize_into / raw pointers | Доверенный быстрый путь | Корректный кадр, достаточные области, правильное выравнивание |
| deserialize_prepared_into | Обновление живого объекта | Ёмкости достаточно для каждого переиспользуемого поля |
| deserialize_reuse | Сохранение поддержанных буферов | Не все схемы имеют одинаковое поведение reuse |

Нельзя записывать новую владеющую строку в живой объект через raw uninitialized-путь без освобождения прежнего значения. Это даст утечку. Для повторного чтения используется prepared/reuse либо корректный Drop перед записью. REUSES_STORAGE показывает поддержанную генератором форму, но не создаёт ёмкость сам.

Курсор каждой схемы проверяет длины, диапазоны, порядок/содержание метаданных, UTF-8, padding, LZ и окончание кадра. Она не добавляет неявную проверку в каждый trusted-вызов. Ошибка встроенного кадра возвращается как QslError, а не должна доходить до unsafe-чтения.

Проверка соответствия форме не является идентификацией схемы. Две схемы с одинаковой допустимой wire-формой могут принять одни байты. Для различения типов нужен согласованный discriminator/версия/handshake. QBProto и идентификатор R пока являются планом.

## SerOut и нативные области

SerOut хранит собственную allocation, ёмкость/длину и выравнивание. new создаёт инициализированную память. with_capacity_aligned оставляет длину нулевой до заполнения. Наблюдать неинициализированные байты нельзя. Trusted serialize_to требует достаточной ёмкости; имя метода не означает автоматическую проверку.

native меняет удобный Serializable::serialize: результатом становится SerOut вместо Vec<u8>. Поскольку тип результата зависит от feature и иногда от сгенерированного inherent-метода, примеры следует сверять с конфигурацией.

Windows NativeRegion — однопоточная bump-область поверх VirtualAlloc. Отдельные buffer/slot не создают heap-allocation на каждую операцию. Заимствования не позволяют reset/drop, пока область используется. Регион намеренно не Send и не Sync. prefault заранее касается страниц; выравнивание и рабочий набор влияют на кеши и пропускную способность.

Скорость зависит от процессора, компилятора, размеров, кешей и памяти. Выравнивание 64 B не доказывает попадание всего набора в L1 и не означает выравнивание каждого нативного объекта.

## SharedRegion и IPC

SharedRegion поддерживает потоки и отдельные процессы Windows. Участники обмениваются смещениями в mapping, а не абсолютными указателями. Запись резервирует область, заполняет байты и публикует завершённое содержимое через release/acquire.

Опубликованные байты неизменяемы; время жизни mapping удерживается владельцами. Резервирование ограничено ёмкостью. Регион не является автоматической очередью с обратным освобождением каждого сообщения. Протокол владения, имена mapping и соглашения о формате задаёт приложение.

Открытие чужого mapping требует доверия к его заголовкам и синхронизации; часть API намеренно unsafe. Разделение процесса не превращает произвольную память в валидный QSL-кадр. Перед pointer-decoding выполняется подходящая валидация.

В обзоре кодеков не подменяются результаты IPC или сокета: эти механизмы имеют отдельную область применения и функциональные проверки. Их системная задержка не выводится из наносекунд сериализатора.

## QSL_RT

```deq
!config QSL_RT = true;
!config QSL_RT_DEFAULT = 16;
```

RT выключен по умолчанию. DEFAULT задаёт количество одновременно занятых слотов на схему, а не байты и не квант. Допустимы 1..64 слота. Статические регионы генерируются только для конечной известной верхней границы; бюджет payload с padding ограничен 64 MiB на схему.

Lease занимает один слот. При исчерпании возвращается PoolExhausted без дополнительного буфера. Drop освобождает слот. CAS и атомарное освобождение имеют собственную цену. RT не означает, что поля исходного String/Vec никогда не выделяют память.

deserialize_into сохраняется. Для общего внешнего ByteQps scratch/output/restoration задаются отдельно; существующий RT-пул внутреннего сообщения не становится автоматически парой внешних QPS-регионов.

## Сокеты

RawSocket использует обычный TCP-объект Rust и бинарные кадры QSL. NativeSocket/NativeListener при native+Windows вызывают WinSock напрямую, поддерживают блокирующие операции, полные send/receive, framing, ограничение размера и таймауты.

Поле max_frame проверяет допустимый размер до выделения/чтения кадра. Ошибки framing и прерванные операции могут завершить пригодность соединения; приложение не продолжает разбор произвольной середины потока как нового кадра. Raw-pointer receive требует достаточной writable-области.

TCP остаётся потоком. Одно чтение не обязано вернуть целое сообщение. Передача QSL не добавляет TLS, HTTP-семантику, согласование схем и авторизацию. Это отдельные уровни приложения; стоимость их выполнения не входит в codec-only замеры.

## Rust-макросы и custom-кодеки

```rust
#[qsl::qsl_macro]
pub struct Meta { pub id: u32, pub tick: u64 }
```

Схема &Packet { Meta meta; u16 code; } получает поля meta_id, meta_tick, code. Оригинальный Rust-тип может оставаться вложенным; поля дублируются в генерируемую структуру. Поддержаны вложенные и повторные шаблоны. Маркеры qsl_macro и schem_macro находятся на Rust-структуре; атрибута [macro] в QSL нет.

Пределы: 64 итоговых поля, глубина 64, отсутствие циклов и конфликтов имён. Групповая optional/default на ссылке неоднозначна; свойства задаются на членах. Generic/cfg и вычисленные ёмкости не угадываются. Произвольное разрешение всех Rust-импортов не реализуется bounded-поиском редактора.

QslCustom задаёт SIZE, COMP_SIZE и методы сырой записи/чтения. Для checked-декодирования нужен qsl_validate; значение по умолчанию отклоняет такой вход. Пользовательский unsafe-код отвечает за инициализацию, точный размер и корректные значения Rust. Неизвестная анализатору ширина ограничивает RT, смещения и оценки размера.

## DEQ, inline и возможности сборки

DEQ поддерживает !define NAME: type = expression; и перечисленные !config. Повторная константа/настройка и неизвестная директива являются ошибкой. Пути файлов остаются в build.rs. Типизированное значение должно помещаться в объявленный целый тип.

inline, inline=hint, inline=always, inline=never — явные политики сгенерированных методов. Без атрибута решение принимает компилятор. Атрибут независим от InlineString и предиктования. always может увеличить код и рабочий набор инструкций; never может оставить вызов; точный эффект определяется сборкой.

rust-macros включает разбор отмеченных Rust-структур. native включает native-выходы и, на Windows с 64-битными атомиками, нативную память/сокет. diagnostics предоставляет отдельные checked-cursor инструменты; он не требуется для автоматически генерируемого checked API. Публичные API и доступные типы следует читать вместе с feature-gates.

## Методика замеров и P

Основной индекс P=M/T: M — объём исходных полезных данных в байтах, T — время на операцию в наносекундах. Единица B/ns численно совпадает с десятичными GB/s. Это производительность обработки, а не доля сжатия.

Для borrowed-результата P оценивает создание представления всего payload. Физический объём чтения может быть гораздо меньше M. Поэтому такой P не измеряет пропускную способность копирования памяти.

Wire-размер показывается отдельно: минимум, максимум и среднее. Для переменного optional-набора M — среднее число полезных байтов при указанном распределении. Заголовок, padding объекта и capacity буфера не добавляются к полезным данным. Чем меньше кадр при той же скорости полезного обмена, тем иной компромисс по памяти/сети; одного P для всех решений недостаточно.

При T в положительном интервале [T_low,T_high] интервал P равен [M/T_high,M/T_low]. Показатели сравниваются только внутри одинаковой задачи. Валидация без создания результата, borrowed-view и создание новой String — разные контракты, даже если рядом показано одинаковое M.

Обзор: 103 разных случая (95 основных и 8 UTF-8/целой записи), 125 наблюдений с учётом повторного замера 22 случаев общего QPS. Остальные 81 случай сохраняют исходный снимок. Criterion, прогрев 15 s каждого случая, измерение 10 s, 200 выборок, CI 99%, лимит 8 GiB. Измерительный поток закрепляется за допустимым ядром, приоритет выше обычного. Подготовка вне измерения, если в названии не указаны allocation/lease. Исходники и бинарный файл зафиксированы SHA-256 до запуска.

«Кардиограмма» показывает T_i=sample_time_i/iterations_i и P_i=M/T_i для каждой выборки. Это не распределение задержек отдельных вызовов и не p99 сетевого запроса. Warm-up не входит в эти точки. Масштаб и единицы подписаны; все исходные sample/estimate доступны.

Оборудование: Windows 11 x86-64, i5-7400, RAM 24 GiB / 2133 MHz. Старые профили с иной схемой, рабочим набором или политикой закрепления ядра остаются отдельными снимками. Из их чисел не строится общий рейтинг.

## Ограничения, доказательства и развитие

Lean4 проверяет арифметические утверждения восстановления ранга, пары частное/остаток, непересекающихся radix-групп и индекса границ opt_table. Утверждения о предиктовании не являются свойством QPS. Lean-файл не доказывает корректность всего Rust/LLVM, аллокатора или IPC.

Проверки общего QPS включают все значения байта, короткие хвосты, UTF-8, high-base, повторы, мутации кадров, неверные ширины, размеры и восстановление разных типов. Наличие таких тестов не позволяет объявлять произвольный custom-код безопасным.

План QBProto предполагает начальное согласование максимума данных и идентичности схем. Уникальный идентификатор нельзя обосновывать только сжатием произведений S×F без точного кодирования множества, порядка и конфигурации. Протокол R требует отдельного определения и анализа коллизий; готовая реализация не заявляется.

Проект развивается как внутреннее решение, зависящее от архитектуры и условий применения. Выбор специальных инвариантов обменивает универсальность на более плоский код. Правильность формата, воспроизводимость и измеренный компромисс важнее универсального обещания ускорения.

## Модель дескрипторов

QslType — внутренняя модель генерации; ParserQslType — адаптер прежнего AST. Это не утверждение, что все варианты имеют отдельный текстовый синтаксис.

| QslType | Rust | Поля дескриптора |
|---|---|---|
| None | () | Нет кодируемого значения |
| Byte | u8 | Нет tuple-полей |
| Integer | integer primitive | bits: разрядность хранения; signed: знаковость; min: прежняя база ранга |
| RangedInteger | integer primitive | bits/signed: хранение; min/max: включительный диапазон |
| Flags | u8/u16/u32/u64 | Flags.0: usize, число битов |
| FixedString | [u8; N] | FixedString.0: usize, точное число UTF-8-байтов |
| String | String or borrowed &str | String.0: usize, прежний минимум; текстовый str использует ноль |
| RangedString | String or borrowed &str | min/max: границы UTF-8-байтов |
| CompressedString | InlineString<MAX> | min/max: границы восстановленных UTF-8-байтов |
| BinaryString | &'a [u8] | min/max: границы UTF-8-байтов, опциональная верхняя граница |

| InlineRawString | InlineString<MAX> | min/max: границы raw inline-байтов |
